# 7회차 과제 — 느낀점 / 배운점

**과제**: Travel Planner 앱 개발 (Cloud LLM · Local LLM)  
**작성일**: 2026-09-28

---

## 배운점

### 1. 외부 API 키는 코드보다 먼저 검증해야 함

이번 과제에서 가장 크게 배운 점임. 앱을 다 만들고 실행하려는 순간 키 3개가 모두 막혀 있었음.

| 키 | 처음 상태 | 원인 | 해결 |
|----|----------|------|------|
| Groq | `expired_api_key` | 키 만료 | 재발급 |
| OpenWeatherMap | `401 Invalid API key` | 발급 직후 활성화 대기 | 시간 경과 후 자동 해결 |
| Google Places | `PERMISSION_DENIED` | 프로젝트에 API 미사용 설정 | Cloud Console에서 사용 설정 |

특히 Google 키는 **키가 잘못된 것이 아니라 프로젝트에서 해당 API를 켜지 않은 것**이었음.  
오류 메시지를 끝까지 읽지 않았으면 키를 다시 발급받는 헛수고를 할 뻔했음.

실제로 그 헛수고를 한 번 했음. API가 막혀 있다고 생각해 **새 키를 발급받았는데**, 새 키는
키 자체에 'API 제한'이 걸려 있어 `Requests to this API ... are blocked` 오류가 났음.
정작 처음 키는 사용 설정이 끝나 정상 동작하고 있었음.

→ 교훈: Google API 오류는 **두 층**에서 날 수 있음. ① 프로젝트에 API가 켜져 있는가,
② 키에 걸린 API 제한이 그 API를 허용하는가. 메시지가 다르므로 구분해서 읽어야 함.

| 메시지 | 의미 |
|--------|------|
| `... has not been used in project ... or it is disabled` | ① 프로젝트에 API 미사용 설정 |
| `Requests to this API ... are blocked` | ② 키의 API 제한에 막힘 |

→ 교훈: 개발 시작 전에 `curl` 한 줄로 각 키를 먼저 찔러볼 것. 실패 응답의 **코드와 메시지를 구분해서**
읽을 것. `401`(인증 실패)과 `403 PERMISSION_DENIED`(권한·설정 문제)는 해결 방법이 완전히 다름.

### 2. LLM이 지어내지 못하게 만드는 것은 프롬프트가 아니라 구조임

"추측하지 말라"고 프롬프트에 쓰는 것만으로는 부족함. 이번에는 아예 구조를 이렇게 잡음.

```text
외부 API 호출 → 결과 확정 → 프롬프트에 주입 → LLM은 "고르고 배치"만 수행
```

LLM에게 검색 권한을 주지 않고 **이미 확정된 목록 안에서만** 고르게 하니 지어낼 여지가 줄었음.
자료가 부족한 경우도 억지로 채우지 말고 `notes`에 사유를 남기도록 스키마에 자리를 만들어 둠.

→ 교훈: 환각을 막는 가장 확실한 방법은 "하지 마라"가 아니라 **할 수 없게 만드는 설계**임.

### 3. Structured Output의 가치는 파싱 제거가 아니라 '누락 감지'임

Pydantic 스키마로 받으면 문자열 파싱이 없어지는 것이 눈에 띄는 이점이지만,
실제로 더 큰 이점은 **모델이 빠뜨린 항목이 즉시 드러난다**는 점임.
자유 문장으로 받으면 "저녁 식당을 안 줬다"를 사람이 읽어야 알지만,
스키마로 받으면 검증 단계에서 바로 걸림.

### 4. 한글 Windows에서 `load_prompt`는 encoding을 명시해야 함

실제로 부딪힌 버그임.

```python
load_prompt(path)                      # UnicodeDecodeError: 'cp949' codec can't decode
load_prompt(path, encoding="utf-8")    # 정상
```

`load_prompt`가 파일을 열 때 OS 기본 인코딩을 쓰기 때문에, 한글 Windows(cp949)에서는
UTF-8로 저장한 한글 프롬프트를 읽지 못함. 같은 코드가 Mac에서는 잘 돌아가므로
"내 PC에서는 됐는데요"가 나오기 딱 좋은 유형의 버그임.

→ 교훈: 파일을 읽는 라이브러리 함수는 **encoding 파라미터가 있는지 먼저 확인**할 것.

### 5. 외부 API는 '되는 검색어'가 따로 있음

Places Text Search에 한글 검색어를 넣으니 결과가 이상했음.

| 검색어 | 결과 |
|--------|------|
| `서울 맛집` | **0건** |
| `경복궁` | 5건이지만 전혀 무관한 가게들 |
| `best restaurants in Seoul, South Korea` | 정상 |
| `tourist attractions in Seoul` | 정상 |

검색어는 영문으로 보내고 `languageCode=ko`를 함께 주면 **결과 이름·주소는 한글로** 받을 수 있음.
"기능이 안 된다"가 아니라 "입력 형태가 맞지 않았다"였음.

→ 교훈: 외부 API가 빈 결과를 주면 키·권한부터 의심하기 전에 **입력값 형태**를 먼저 바꿔 볼 것.

### 6. 구조화 출력은 길이 한도에 취약함

앱이 완성된 뒤 첫 실행에서 이 오류가 났음.

```
Failed to parse tool call arguments as JSON
```

JSON이 깨진 게 아니라 **응답이 중간에 잘린 것**이었음. 실패 메시지에 찍힌 생성 내용을 보니
2일차 점심 식당 주소를 쓰다가 끊겨 있었음. `max_tokens=16384`로 올려 해결함.

한국어는 같은 내용이라도 토큰을 많이 먹고, 구조화 출력은 필드명·따옴표까지 토큰을 쓰므로
자유 문장보다 훨씬 길어짐. 스키마가 커질수록 출력 한도를 함께 키워야 함.

→ 교훈: 구조화 출력에서 JSON 파싱 오류가 나면 **모델 품질보다 길이 한도를 먼저 의심**할 것.

그리고 Local LLM에서 **똑같은 증상이 다시 났는데 원인 층이 달랐음**.

```
Failed to parse TravelPlan ... days.1.estimated_cost_krw  Field required
```

"모델이 필드를 빠뜨렸다"로 보이지만 실제로는 응답이 `"g_mp="` 에서 잘린 것이었음.
Ollama는 모델이 128k를 지원해도 **기본 컨텍스트를 4096 토큰으로 잡음**.
`num_ctx=16384`, `num_predict=8192`로 올려 해결함.

| 런타임 | 막힌 지점 | 고친 값 |
|--------|----------|---------|
| Groq (Cloud) | 출력 토큰 한도 | `max_tokens=16384` |
| Ollama (Local) | 입력+출력 합친 컨텍스트 창 | `num_ctx=16384` |

→ 교훈: 증상이 같아도 **런타임마다 조절할 손잡이가 다름**. Cloud는 출력 한도,
Local은 컨텍스트 창을 봐야 함. "Field required"가 뜨면 진짜 누락인지
**잘림인지부터 원문 끝을 눈으로 확인**할 것.

### 7. 문서의 모델명을 그대로 믿지 말 것

과제 예시는 `llama-3.3-70b-versatile`이었지만 실제 계정에는 그 모델이 없었음.
제공 목록을 조회해 보니 이랬음.

```
채팅 가능 : openai/gpt-oss-120b, openai/gpt-oss-20b, qwen/qwen3.8-27b, allam-2-7b
채팅 불가 : whisper-large-v3(음성), llama-prompt-guard-2-*(안전성 분류 전용)
```

이름에 `llama`가 들어갔다고 대화용 모델이 아니었음. `prompt-guard`는 분류기임.

→ 교훈: 모델명은 계정·시점에 따라 다름. `/v1/models`로 **실제 목록을 조회해서** 고를 것.

### 8. 설치에 관리자 권한이 필요하면 다른 길을 찾아볼 것

Ollama를 WSL에 넣으려다 두 번 막혔음.

1. 공식 설치 스크립트가 `sudo`를 요구 → 비밀번호 입력에서 멈춤
2. 무권한 설치로 우회하려 했으나 배포 파일이 `.tar.zst`로 바뀌었고 WSL에 `zstd`가 없었음
   (zstd 설치에 또 sudo 필요)

결국 **Windows용 zip을 받아 홈 디렉토리에 풀어** 해결함. 관리자 권한이 필요 없고,
Windows 가상환경 앱이 `localhost:11434`로 바로 붙어 오히려 단순했음.

→ 교훈: "설치 = 관리자 권한"이 아님. 압축만 풀면 되는 배포본이 있는지 먼저 확인할 것.

### 9. Cloud LLM과 Local LLM은 코드가 거의 같지만 '설정 검증'이 다름

체인 구조는 모델 객체만 바꾸면 그대로 재사용 가능했음 (`ChatGroq` → `ChatOllama`).
하지만 실행 전 점검해야 할 것이 달랐음.

- Cloud: API 키가 있는가
- Local: **Ollama가 떠 있는가 + 모델이 받아져 있는가**

Local 버전은 "키 없음" 대신 "서버 안 떠 있음 / 모델 없음"이라는 실패가 생기므로,
`/api/tags`를 먼저 호출해 확인하고 `ollama pull` 명령을 안내하도록 만듦.

또 4B 모델은 도구 호출이 불안정해 `method="json_schema"`를 지정하고,
장소 후보 수를 10개 → 6개로 줄여 컨텍스트 부담을 낮춰야 했음.

→ 교훈: 같은 기능이라도 **런타임이 바뀌면 실패 모드가 바뀜**. 실패 모드에 맞춰 사전 점검을 다시 설계해야 함.

### 10. LCEL은 흐름이 코드에 그대로 보임

```python
chain = gather | prompt | structured_llm
result = chain.invoke(user_input)
```

이 한 줄이 "자료 모으고 → 프롬프트 만들고 → 모델에 넣는다"를 그대로 표현함.
중간에 단계를 끼워 넣거나 빼기도 쉬웠음. 파이프 연산자가 문서 역할까지 함.

## 느낀점

### 막힌 곳을 정확히 아는 것이 결국 가장 빠른 길이었음

코드를 다 짜고 실행하려는 순간 키 3개가 모두 막혀 있었음. 그때는 "아무것도 못 했다"고 느꼈지만,
막연히 "안 돼요"로 남겨 두지 않고 **세 가지 모두 원인을 문장으로 특정**해 둔 것이 결정적이었음.

- "Groq 키가 만료됨(`expired_api_key`)"
- "OpenWeatherMap 키가 아직 활성화되지 않음"
- "Places API가 프로젝트 121898617089에 사용 설정되어 있지 않음"

이렇게 적어 두니 각각 누가 무엇을 하면 되는지가 분명했고, 조치가 끝나자마자 바로 실행으로
이어졌음. 결국 세 가지 모두 해결되어 앱을 끝까지 돌렸음.

→ 교훈: 막혔을 때 "안 된다"가 아니라 **"무엇이 왜 안 되는지"까지 좁혀 두면**, 그 자체가 진도임.

### "동작 확인"의 기준을 낮추지 않기

중간에 "코드가 임포트되고 프롬프트가 포맷된다"까지 확인한 시점이 있었음. 그것을 "앱이 동작한다"고
부르고 싶은 유혹이 있었지만 그러지 않았음. 실제로 그 상태에서 실행했더니 응답 잘림 오류가 났고,
한글 검색어 문제도 그때는 드러나지 않았음. 즉 **임포트 성공은 동작의 근거가 전혀 아니었음**.

외부 API 응답을 실제로 받고 LLM이 계획을 끝까지 돌려준 것만 동작으로 인정하니,
버그 3건이 모두 그 마지막 단계에서 잡혔음. 공통지침의 '정직한 보고 규칙'이 기준 역할을 해 줬음.

### 작은 모델의 한계를 설계로 흡수하기

`gemma3:4b`와 `gpt-oss-120b`를 같은 조건으로 돌려 보니 차이가 뚜렷했음.

`num_ctx`를 올려 양쪽 모두 끝까지 생성시킨 뒤, 같은 조건(서울 1박 2일, 2명, 40만원)으로 비교함.

| 항목 | Cloud (gpt-oss-120b) | Local (gemma3:4b) |
|------|---------------------|-------------------|
| 세 끼 채움 | 3끼 | 3끼 (컨텍스트 상향 후 해결) |
| 시간대 표기 | `아침` `점심` `저녁` | `breakfast` `lunch` `dinner` (한국어 지시 무시) |
| 장소 분류 | 관광지·식당 정확히 구분 | 식당(정식당)을 관광지 목록에 배치 |
| 중복 회피 | 날짜별로 다른 장소 | N서울타워를 1·2일차에 모두 배치 |
| 예산 준수 | 1일차 13만 + 2일차 13만 = 26만 (40만 이내) | 양일 각 35만 → 합계 70만 (**예산 초과**) |
| 추천 이유 | 그날 날씨·동선과 연결해 서술 | "4.4점의 평점을 받은" 형태 반복 |
| 소요 시간 | 약 20초 | 약 10분 (CPU) |

다만 **환각은 양쪽 모두 없었음**. 장소 이름·주소·평점·지도 링크는 4B 모델에서도
Google Places 응답 그대로였고, 목록에 없는 장소를 지어내지 않았음.
`notes`에 "1일차는 흐리므로 실내 관광 우선" 같은 근거도 스스로 남겼음.

→ 교훈: 작은 모델에서 무너진 것은 **사실성이 아니라 지시 이행력**이었음.
"자료 안에서만 고르게 하는" 설계는 모델 크기와 무관하게 작동했고,
반대로 "한국어로 써라", "예산을 넘기지 마라" 같은 **계산·형식 지시는 지켜지지 않았음**.
→ 사실성은 설계로, 형식은 스키마 제약(enum 등)으로 잡는 것이 맞음.
프롬프트 문장에만 의존하면 작은 모델에서 먼저 무너짐.

### 클론 코딩의 의미

`app/` 코드를 `app-clone/`에 다시 옮기며 각 파일이 왜 그 자리에 있는지 다시 보게 됐음.
`config.py`가 왜 별도 파일인지, 프롬프트를 왜 YAML로 뺐는지, 처음 쓸 때는 관행처럼 했지만
두 번째로 훑으니 이유가 붙었음.
