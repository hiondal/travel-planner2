# 7회차 과제 — 느낀점 / 배운점

**과제**: Travel Planner 앱 개발 (Cloud LLM · Local LLM)  
**작성일**: 2026-09-28

---

## 배운점

### 1. 외부 API 키는 코드보다 먼저 검증해야 함

이번 과제에서 가장 크게 배운 점임. 앱을 다 만들고 실행하려는 순간 키 3개가 모두 막혀 있었음.

| 키 | 상태 | 원인 |
|----|------|------|
| Groq | `expired_api_key` | 키 만료 |
| OpenWeatherMap | `401 Invalid API key` | 미활성 또는 오류 |
| Google Places | `PERMISSION_DENIED` | 키는 유효하나 프로젝트에 API 미사용 설정 |

특히 Google 키는 **키가 잘못된 것이 아니라 프로젝트에서 해당 API를 켜지 않은 것**이었음.  
오류 메시지를 끝까지 읽지 않았으면 키를 다시 발급받는 헛수고를 할 뻔했음.

→ 교훈: 개발 시작 전에 `curl` 한 줄로 각 키를 먼저 찔러볼 것. 실패 응답의 **코드와 메시지를 구분해서**
읽을 것. `401`(인증 실패)과 `403 PERMISSION_DENIED`(권한·설정 문제)는 해결 방법이 완전히 다름.

### 2. LLM이 지어내지 못하게 만드는 것은 프롬프트가 아니라 구조임

"추측하지 말라"고 프롬프트에 쓰는 것만으로는 부족함. 이번에는 아예 구조를 이렇게 잡음.

```text
외부 API 호출 → 결과 확정 → 프롬프트에 주입 → LLM은 "고르고 배치"만 수행
```

LLM에게 검색 권한을 주지 않고 **이미 확정된 목록 안에서만** 고르게 하니 지어낼 여지가 줄었음.
자료가 부족한 경우도 억지로 채우지 말고 `notes`에 사유를 남기도록 스키마에 자리를 만들어 둠.

→ 교훈: 환각을 막는 가장 확실한 방법은 "하지 마라"가 아니라 **할 수 없게 만드는 설계**임.

### 3. Structured Output의 가치는 파싱 제거가 아니라 '누락 감지'임

Pydantic 스키마로 받으면 문자열 파싱이 없어지는 것이 눈에 띄는 이점이지만,
실제로 더 큰 이점은 **모델이 빠뜨린 항목이 즉시 드러난다**는 점임.
자유 문장으로 받으면 "저녁 식당을 안 줬다"를 사람이 읽어야 알지만,
스키마로 받으면 검증 단계에서 바로 걸림.

### 4. 한글 Windows에서 `load_prompt`는 encoding을 명시해야 함

실제로 부딪힌 버그임.

```python
load_prompt(path)                      # UnicodeDecodeError: 'cp949' codec can't decode
load_prompt(path, encoding="utf-8")    # 정상
```

`load_prompt`가 파일을 열 때 OS 기본 인코딩을 쓰기 때문에, 한글 Windows(cp949)에서는
UTF-8로 저장한 한글 프롬프트를 읽지 못함. 같은 코드가 Mac에서는 잘 돌아가므로
"내 PC에서는 됐는데요"가 나오기 딱 좋은 유형의 버그임.

→ 교훈: 파일을 읽는 라이브러리 함수는 **encoding 파라미터가 있는지 먼저 확인**할 것.

### 5. Cloud LLM과 Local LLM은 코드가 거의 같지만 '설정 검증'이 다름

체인 구조는 모델 객체만 바꾸면 그대로 재사용 가능했음 (`ChatGroq` → `ChatOllama`).
하지만 실행 전 점검해야 할 것이 달랐음.

- Cloud: API 키가 있는가
- Local: **Ollama가 떠 있는가 + 모델이 받아져 있는가**

Local 버전은 "키 없음" 대신 "서버 안 떠 있음 / 모델 없음"이라는 실패가 생기므로,
`/api/tags`를 먼저 호출해 확인하고 `ollama pull` 명령을 안내하도록 만듦.

또 4B 모델은 도구 호출이 불안정해 `method="json_schema"`를 지정하고,
장소 후보 수를 10개 → 6개로 줄여 컨텍스트 부담을 낮춰야 했음.

→ 교훈: 같은 기능이라도 **런타임이 바뀌면 실패 모드가 바뀜**. 실패 모드에 맞춰 사전 점검을 다시 설계해야 함.

### 6. LCEL은 흐름이 코드에 그대로 보임

```python
chain = gather | prompt | structured_llm
result = chain.invoke(user_input)
```

이 한 줄이 "자료 모으고 → 프롬프트 만들고 → 모델에 넣는다"를 그대로 표현함.
중간에 단계를 끼워 넣거나 빼기도 쉬웠음. 파이프 연산자가 문서 역할까지 함.

## 느낀점

### 막힌 곳을 정확히 아는 것도 진도임

키 3개가 모두 막혀 앱을 끝까지 돌려보지 못했음. 처음에는 "아무것도 못 했다"고 느꼈지만,
**무엇이 왜 막혔는지 세 가지 모두 원인을 특정**했고 각각 해결 방법도 확인했음.
막연히 "안 돼요"와 "Places API (New)가 프로젝트 121898617089에 사용 설정되어 있지 않음"은
전혀 다른 상태임. 후자는 다음 행동이 명확함.

### "동작 확인"의 기준을 낮추지 않기

코드가 임포트되고 프롬프트가 포맷되는 것까지는 확인했지만, 그것을 "앱이 동작한다"고
부르지 않기로 했음. 외부 API 응답을 실제로 받고 LLM이 계획을 돌려준 것만 동작으로 인정함.
공통지침의 '정직한 보고 규칙'이 이런 상황에서 기준 역할을 해 줬음.

### 작은 모델의 한계를 설계로 흡수하기

`gemma3:4b`는 4B 규모라 복잡한 스키마를 채우다 항목을 빠뜨릴 수 있음.
이것을 "모델이 나쁘다"로 끝내지 않고, 후보 수를 줄이고 출력 방식을 바꾸고
README에 대체 모델을 안내하는 식으로 **설계와 문서로 흡수**하는 경험이 됐음.

### 클론 코딩의 의미

`app/` 코드를 `app-clone/`에 다시 옮기며 각 파일이 왜 그 자리에 있는지 다시 보게 됐음.
`config.py`가 왜 별도 파일인지, 프롬프트를 왜 YAML로 뺐는지, 처음 쓸 때는 관행처럼 했지만
두 번째로 훑으니 이유가 붙었음.
